# Spike A, A5 evidence (2026-11-14)

Question: can an agent call rancher-ai-mcp, with a read-only Rancher token, through Amazon
Bedrock AgentCore Gateway, without exposing the server to the internet?

Setup (the spike's `setup_gateway.py apply`, run by the human in the admin terminal):

- rancher-ai-mcp v1.2.0-alpha.5 (commit 46f49c7e4e296e003b01c05ab97fb918c733cb49), built for
  x86 on the spike instance, run as `mcp serve --insecure --read-only --port 9092` with
  `RANCHER_URL=https://127.0.0.1` (plain HTTP inside the VPC; outside a cluster its HTTP mode
  needs `--insecure`, which also skips the check of Rancher's certificate on the same host).
- Internal ALB `mcp-spike` (zones use1-az6 and use1-az1; the instance is in use1-az6) with a
  public ACM certificate for `mcp-spike.<domain>`, HTTPS 443, forwarding to the instance on
  9092. `routing.http.drop_invalid_header_fields.enabled` is false. Only the ALB's security
  group may reach port 9092; the ALB takes HTTPS from the VPC CIDR only.
- AgentCore Gateway `rancher-spike`: protocol MCP, inbound AWS_IAM.
- Target `rancher`: endpoint `https://mcp-spike.<domain>/mcp`; outbound auth API_KEY from the
  credential provider `rancher-spike`, sent in the header `R_token` with no prefix; private
  endpoint `managedVpcResource` (IPv4, two subnets, one security group) with `routingDomain`
  set to the internal ALB's DNS name.
- Gateway role `rancher-spike-gateway`: `GetWorkloadAccessToken`, `GetResourceApiKey` and
  `secretsmanager:GetSecretValue` on the provider's secret only.

| Check | Result |
|---|---|
| Target creation (DEFAULT listing mode) | READY; the ALB counted 5 requests, all 2XX (tool discovery through the private endpoint) |
| `tools/list` through the gateway (mcp-proxy-for-aws-cli 1.8.0, SigV4) | 29 tools, prefixed `rancher___` (the server's `--read-only` set) |
| First `tools/call` (`rancher___listKubernetesResources`, namespaces of `local`) | `isError: True`, "An internal error occurred. Please retry later." |
| Cause (CloudTrail) | The gateway role was refused `bedrock-agentcore:GetResourceApiKey` on its own workload identity, `workload-identity-directory/default/workload-identity/rancher-spike-<id>`; `GetWorkloadAccessToken` was allowed. At target creation the same lookups ran as the caller (the admin), so creation succeeded. |
| Fix | Added the workload-identity ARNs to the role's `GetResourceApiKey` statement |
| Second `tools/call` | `isError: False`; 20 namespaces of `local`, the same as A4's direct call. The ALB counted 4 more requests, all 2XX; CloudTrail shows `GetResourceApiKey` by the gateway role allowed. |
| Unsigned `POST` to the gateway URL | HTTP 401 |
| Header check on: `drop_invalid_header_fields` set to true on the spike ALB, then the same call 30 s later | `isError: True`; the server answered that the client must provide credentials, because the ALB dropped `R_token` |
| Header check off again, then the same call 30 s later | `isError: False`; the 20 namespaces again |

Findings:

1. The design works end to end with nothing open to the internet: AgentCore Gateway reaches a
   self-hosted MCP server in the VPC through a managed VPC Lattice endpoint, verifies a
   public ACM certificate on an internal ALB (no custom CA), and injects the Rancher token
   from an API key credential provider into the header rancher-ai-mcp expects.
2. AWS's documented example policy for an API key credential provider is incomplete:
   `GetResourceApiKey` is also authorized against the gateway's workload identity.
3. A target can be READY while every tool call fails: discovery at creation uses the caller's
   credentials, invocations use the gateway role. Test with a real tool call.
4. `R_token` contains an underscore. An ALB with `drop_invalid_header_fields` enabled drops it (the
   header-check rows above show it),
   and the lab's Rancher ALB (`infra/aws/lab/load_balancers.tf`) enables it. A shared ALB would
   silently strip the token; use a dedicated ALB or listener without that setting, or the
   server's OAuth mode (`Authorization: Bearer`).
5. An ALB routes only to targets in its own zones; Lattice's managed endpoint accepts subnets
   only in use1-az1, az2, az4, az5 and az6. Zone names map to zone IDs per account.
6. In HTTP mode rancher-ai-mcp returns `uiContext` alongside `llm` (stdio mode strips it), so
   responses are larger.
7. mcp-proxy-for-aws's `--read-only` relies on tool annotations, which rancher-ai-mcp does not
   set (see A4), so it would hide every tool. Rely on the server's `--read-only` and Rancher's
   RBAC.

The spike's scripts (`configure_spike_rancher.py`, `rancher-mcp.sh`, `mcp_probe.py`,
`setup_gateway.py`, `teardown.py`) ran from the git-ignored `build/spike-a/` and land in a
follow-up pull request under `tools/spikes/spike-a/`.

Teardown (A6, 2026-11-14): `teardown.py apply` removed the gateway, its target and credential
provider, the role, the load balancer, target group, certificate and validation record, the
security groups, the instance, its key pair and the default VPC, and on the Mac the Keychain
items, the spike's files and the local image. A read-only check afterwards found none of them
left, and no VPC Lattice resource gateway.
